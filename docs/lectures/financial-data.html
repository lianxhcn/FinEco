2  金融数据分析：流程、环境与数据获取

假设我们想研究企业负债与盈利能力的关系。最直接的做法似乎是打开数据库，下载资产、负债和利润，再开始回归。但真正进入数据以后，很快就会碰到一连串更具体的问题：研究对象是全部上市公司，还是某个行业？使用合并报表还是母公司报表？盈利能力看当年还是下一年？一条财务数据在什么时候才真正对投资者可见？

这些问题看起来发生在数据处理阶段，实际上都在界定研究问题本身。数据能下载下来，只说明我们取得了某些记录，并不说明这些记录已经适合回答手头的问题。因此，本讲不把会调用几个接口当作数据获取的终点，而是从研究问题出发，说明怎样把一个研究设想逐步翻译成可以检查、可以复现的数据需求。

本讲沿着这一思路展开：先看一项数据分析从问题到结论要经过哪些环节，再区分我们面对的是哪一类数据、不同工具分别负责什么，最后进入文件、数据库和 API 等具体获取方式。《数据分析与经济决策》课程的流程、数据、工具与 AI和金融数据获取提供了主要基础；这里在此之上增加金融计量研究更关心的样本口径、信息时间和可审计性。

本讲要点
  1. 把研究问题写成可以核对的数据需求。
  2. 区分数据结构、数据来源与具体获取工具。
  3. 理解语言、Notebook、Quarto、Git/GitHub 和 Agent 在工作流中的分工。
  4. 为后续管理、清洗和建模保存可复查的输入快照。

后续依次学习数据管理、清洗与审计，最后完成 CSMAR 实战。

2.1 数据分析的基本流程

数据分析很少从一个已经写得十分精确的问题开始。更常见的情形是，我们先有一个大致想法，例如「负债较高的企业是不是盈利较差」，然后才在查资料、看数据和尝试分析的过程中，把这个想法逐步变成可以用证据回答的问题。

仍以这个例子为例。我们至少要说明比较哪些企业，负债和盈利采用什么口径，是比较同一年的相关关系，还是用今年的负债解释下一年的盈利。更进一步，如果问题是「提高负债是否会导致盈利下降」，那就已经从描述性关系进入因果问题，后面的样本设计、控制变量和识别条件都会随之改变。这个区分必须在建模之前想清楚，而不是等回归表出来以后再为系数寻找解释。

图 2.1 给出了一条从问题定义到报告复现的基本路径。图中的虚线尤其重要，因为真实的数据分析很少严格按照一步做完再进入下一步的方式推进。比如，我们原来计划研究 2010—2025 年，但下载后才发现某个核心指标从 2018 年才开始披露。这时可能要缩短研究时期，也可能要换一个更早可得的指标，还可能意味着原来的研究问题需要调整。

这里不能简单地让代码把 2010—2017 年补出来。数据分析中的很多困难，本质上不是编程问题，而是研究定义与可得证据之间出现了不匹配。遇到这种情况，应回到前面的研究问题重新判断。

阶段 需要完成什么 在企业负债例子中要问什么 留下什么
问题定义 把宽泛主题转成具体问题 描述关系、预测盈利，还是识别因果作用？ 研究问题与目标总体
数据获取 按对象、期间、频率取得资料 是否保留退市企业？需要哪种报表？ 原始文件、来源与下载条件
管理和清洗 统一可确认的结构，诊断异常 一行是证券年度还是公司年度？ 字典、代码与样本流
探索性分析 看分布、趋势和组间差异 差异是否由行业或异常分母驱动？ 描述统计与诊断解释
建模分析 使模型对应研究目标 回归系数是否有因果含义？ 模型设定和可执行程序
解读与评价 解释数量级、误差与适用范围 统计差异是否具有经济意义？ 结论、替代解释与局限
报告与复现 让别人理解并检查分析 别人能从同批输入得到同样输出吗？ Notebook、环境与运行说明

同一批变量，可以服务于完全不同的研究任务，但不同任务对应的证据标准并不相同。以负债率和 ROA 为例，可以分别从三个角度使用：

  • 描述：说明样本中企业负债率和盈利能力的分布、差异与相关关系。至少要交代样本覆盖、变量口径和统计范围。
  • 预测：用当前或历史信息预测未来盈利。需要区分训练期与测试期，并确保预测时只使用当时已经能够获得的信息。
  • 因果分析：研究负债变化是否会导致盈利变化。除了变量和样本定义，还要说明为什么观察到的差异能够解释为因果作用。

因此，模型形式本身不会自动决定研究问题。一套预测准确率很高的代码，即使改成回归形式，也不会因此获得因果含义。

2.2 数据类型与结构

在讨论用什么软件、调用什么函数之前，先要判断我们拿到的到底是什么数据。外表相似的对象，进入分析时可能需要完全不同的处理。一个 PDF 页面看起来像规整表格，并不意味着其中的单元格已经是可以直接计算的数据；六位证券代码虽然由数字组成，它的作用仍然是标识证券，而不是一个有大小意义的数值变量。

这一步看似基础，却决定了后续很多处理是否合理。数据类型不是由外表决定的，而是由它在研究中的含义和结构决定的。

2.2.1 按结构化程度区分

最容易进入统计分析的是结构化数据。典型例子是公司年度财务表：每一行对应一家公司的某一个年度，每一列都有相对明确的含义和类型。只要粒度、主键和字段定义已经确认，这类数据可以直接进入后续的筛选、合并和建模。

半结构化数据也包含明确的信息组织规则，只是它不一定表现为二维表格。例如 JSON、XML、HTML 和 XBRL 通常带有键、标签或层级。处理这类数据时，关键不是简单地转成 DataFrame，而是先理解层级关系，再决定哪些字段应该展开成表格。公告正文、电话会议音频和图片等非结构化资料则更进一步：在进入回归之前，我们还需要定义怎样从原始内容中提取或测量变量。

类型 金融例子 进入分析前的关键工作
结构化 股票日行情、年度财务表 检查键、类型、单位与时间
半结构化 API 的 JSON 响应、XBRL 财报 识别层级、提取字段、保留关联
非结构化 年报段落、公告扫描件、电话会议音频 转录或解析，再定义和验证测量规则

这三类数据的差别，直接看一个极小例子会更清楚。假设我们都在描述同一只股票。结构化行情表已经把变量排成固定的行和列：

stock_code date close volume
000001 2026-09-11 12.18 1832000
000001 2026-09-14 12.31 2056000
000001 2026-09-15 12.35 1823400

半结构化数据可能以 JSON 返回。同样的信息仍然有明确字段，但字段可以嵌套在不同层级中：

{
  "stock_code": "000001",
  "date": "2026-09-15",
  "quote": {"close": 12.35, "volume": 1823400},
  "source": "demo"
}

非结构化数据则可能只是一段公告文字，其中没有现成的 close、risk 或 event 列：

公司公告节选（虚构）：
受主要原材料价格上涨影响，本期生产成本有所增加。
公司已与核心供应商协商新的采购安排，
相关安排对下一年度成本的影响仍存在不确定性。

把三种形态放在一起看，进入分析前需要补的工作逐步增加：

  • 对结构化表，可以直接选择 close 等字段进入计算，但仍要检查键、单位和时间口径。
  • 对 JSON，需要先理解层级关系，再把嵌套字段解析成适合分析的变量。
  • 对公告文字，需要先定义要测量的概念，再设计提取或标注规则。

结构越弱，研究者需要补充的测量规则通常越多。

表格与文本可以共同提供信息。例如，资产负债表给出债务存量，附注解释债务期限和抵押条件。结合这些资料称为多模态分析的一种情形。它增加信息，也增加匹配和测量环节；模型提取的风险标签仍需验证，见文本变量的测量。

2.2.2 按时间维度与生成方式区分

另一种常见分类是看数据如何沿着对象和时间两个维度展开。下面三张小表使用虚构数据，只看每一行怎样排列，就可以区分截面、时间序列和面板。

截面数据：同一时期比较多个对象。 例如，在 2025 年末比较三家公司的资产负债率：

firm year leverage
A 2025 0.42
B 2025 0.67
C 2025 0.51

这里时间基本固定，变化主要来自不同企业。

时间序列：同一对象跨多个时期。 例如，跟踪某个市场指数连续四个交易日的收益率：

date index_return
2026-09-10 0.004
2026-09-11 -0.006
2026-09-14 0.009
2026-09-15 0.002

这里对象基本固定，变化主要来自时间。

面板数据：多个对象跨多个时期。 例如，同时观察 A、B 两家公司在两个年度的资产负债率：

firm year leverage
A 2024 0.40
A 2025 0.42
B 2024 0.63
B 2025 0.67

面板数据同时保留企业维度和时间维度，因此一行通常要由对象标识和时间变量共同识别。需要说明的是，面板数据并不要求每家公司都有完全相同的年份。某家公司晚几年才上市，另一家公司中途退市，都会造成不平衡面板。因此，发现某个公司缺少若干年份时，不能立即把它判定为数据遗漏，还要结合上市状态、披露制度和数据库覆盖范围判断。

还可以按照数据是怎样产生的来区分。观测数据来自企业、投资者和市场的实际活动，研究者通常只是记录已经发生的结果；实验数据则来自研究者主动安排的干预和分配。所谓准实验，强调的是研究设计试图利用政策变化、制度边界或其他外部冲击来建立近似实验的比较，而不是某一种特殊的文件格式。

因此，不能因为一份数据被称为准实验数据，就跳过外生性和识别条件的讨论；也不能因为拥有面板数据，就认为混杂因素会自动消失。数据的结构告诉我们信息怎样排列，研究设计才决定这些信息最终能够支持什么样的结论。

2.3 从 DGP 到研究数据

现在进一步追问一个更基本的问题：数据库里的一行记录，与现实经济活动之间到底隔了几层？以企业财务数据为例，可以把研究数据的形成过程拆成四层：

  • 经营活动：企业在真实经营过程中形成收入、成本、资产、负债等经济结果。
  • 记录与披露：会计准则和披露制度决定这些活动怎样被确认、计量和报告。
  • 数据库整理：数据提供方按照自己的字段体系、报表口径、时间规则和版本规则整理公开或授权资料。
  • 研究者筛选：研究者再根据研究问题选择公司、年份、报表类型和变量，形成最终使用的数据。

所以，我们下载到的表格并不是现实世界本身，而是现实活动经过记录、披露、整理和筛选以后留下的可观测结果。理解这一点，是后面讨论样本选择、变量测量和信息时间的基础。

在计量经济学中，我们常用数据生成过程 (data-generating process, DGP) 来描述变量怎样由经济环境、行为选择和随机因素共同形成。比如企业利润会受到产品需求、成本结构、融资条件和经营决策的影响，这些因素共同决定了真实世界中的利润结果。

但研究者最终能否在 CSV 中看到这条利润记录，还要经过另一条链条：企业是否属于数据库覆盖范围，相关信息是否需要披露，数据库是否正确收录，以及我们下载时选择了哪些样本条件。换言之，经济结果怎样产生和研究数据怎样进入样本是两个相关但不同的问题。

读 图 2.2 时，可以沿着图中的过程连续问三个问题：

  1. 覆盖：哪些企业或交易本来就有机会进入记录系统？
  2. 测量：数据库中的变量究竟测量了现实活动的哪一个方面？
  3. 选择：研究者又通过样本条件保留了哪些记录？

这三个问题分别对应后面反复出现的覆盖范围、变量测量和样本选择。

它们中的任何一个环节出现偏差，都可能改变我们最后看到的样本。更重要的是，这类问题不能靠多写一条清洗命令来自动修复，因为是否应该保留、如何解释，仍然取决于研究对象和变量定义。

例如，我们口头上说想研究「某年所有企业的盈利能力」，但实际使用的是上市公司数据库。此时至少有三层样本限制：

  • 数据库覆盖：大量非上市企业一开始就不在数据库覆盖范围之内。
  • 企业退出：经营困难的公司可能在样本期内退市，因此历史记录并不天然构成平衡样本。
  • 下载筛选：如果下载界面只保留当前上市公司，那些过去曾经存在、后来退出市场的企业还会被进一步排除。

在这种情况下，软件仍然可以把样本均值计算到很多位小数，但计算精确并不等于研究对象定义正确。真正需要确认的是：这个均值究竟代表哪一类企业。

用一个简单记号表达这个区别。令 \(S_{it}\) 表示企业 \(i\) 在年份 \(t\) 是否进入最终样本，进入为 1，否则为 0；\(Y_{it}\) 表示这一年的某个结果，如以比例表示的盈利能力。我们实际观察到的平均水平对应 \(E(Y_{it}\mid S_{it}=1)\)。总体平均水平是 \(E(Y_{it})\)。如果是否入样与盈利状况有关，两者一般不能直接画等号。

这里写期望，只是为了把样本平均和目标总体平均之间的区别表达清楚，并不是要求现在建立一个回归模型。它提醒我们，样本选择本身就是研究设计的一部分。样本量再大，也只能让我们更精确地描述这个已选择样本；它不会自动证明样本能够代表原先想讨论的总体。

将下载条件写进研究记录

保存数据库名称、导出时间、样本范围、起止期间、字段、频率及报表类型。下载时间未知时明确记为 unknown。文件的本次读取日期不能冒充最初下载日期。

2.4 环境与工具：每一层负责什么

学到这里，另一个常见困惑是工具越来越多：Python、Stata、Jupyter、Quarto、Git、GitHub、Agent 分别是做什么的？初学者容易把它们看成一组需要选一个的软件，或者认为安装得越多越完整。其实，这些工具处在不同层次，很多时候是配合使用，而不是互相替代。

对一项可复现的数据分析来说，更关键的是弄清楚三件事：数据存放在哪里，哪一个环境真正执行代码，最终结果又通过什么方式保存和发布。只要这三层关系清楚，工具选择就容易得多。

2.4.1 语言、编辑器、内核与报告

本课程用 Stata 讲主要计量方法，用 Python 处理数据；R 也是统计研究中的常用语言。选择应依据已有工作流、方法实现与团队协作，不需要为了使用 Agent 放弃已经熟悉的软件。

层次 常用工具 作用 本课程中的位置
编程与统计语言 Python、Stata、R 执行数据处理、计算和模型估计 方法和数据任务使用对应语言
编辑器 VS Code 等 编写与查看代码、Markdown 和配置文件 可以使用熟悉的编辑器或 Codex 工作区
Notebook Jupyter 将说明、代码和输出放在同一文档 Python 实验的执行与展示载体
内核与环境 Python kernel、Conda 环境、nbstata 等 决定代码真正由哪个解释器和依赖环境执行 决定导入哪个包、使用哪个版本
报告与出版 Quarto 把 Markdown、代码输出和交叉引用渲染为网页或文档 课堂展示读取已保存结果，不实时取数
版本控制与协作 Git、GitHub 记录文件变化、共享代码与协作 受限数据库不进入公共仓库

如果这些名称还比较陌生，可以先用已有课程材料补齐操作层面的背景：

  • Python 安装和环境配置：理解 Python、Anaconda 与 VS Code 的基本关系。
  • Jupyter Notebook 的使用：理解代码单元、Markdown 单元和运行输出怎样放在同一份文档中。
  • 虚拟环境管理：理解环境、包和 Jupyter 内核为什么必须对应。

本章只解释这些工具在研究工作流中的分工，不把环境安装本身作为课堂重点。

Jupyter Notebook 尤其容易造成一种错觉：屏幕上既有代码又有输出，看起来像是一个已经完整执行过的分析。实际上，Notebook 中的代码可能没有运行，保存下来的输出也可能来自更早的版本。若修改了前面的单元，却只重新运行后面的几个单元，还可能把旧变量保留在内存中，形成所谓的隐藏状态。

因此，课前或提交前的可靠检查不是逐格点到不报错，而是重启内核，从头到尾顺序执行一次。若包已经安装成功，但 Notebook 仍提示无法导入，也应先检查当前 Notebook 所使用的内核是否就是安装该包的 Python 环境，而不是马上升级或重装整个环境。

Python 中，pandas 负责表格操作，NumPy 提供数组计算，绘图库负责图形，统计或机器学习包负责模型。数据获取库处在上游，不能代替数据字典或质量检查。后面的 CSMAR 案例使用 pandas 与 Parquet，数据以本地授权快照为输入。

2.4.2 版本控制与复现

可复现分析还需要回答这个结果是怎样一步步变成现在这样的。这里要先区分两个容易混在一起的工具：

  • Git 是版本控制系统，主要在本地记录代码、文档和规则怎样变化。初学者可以先读 Pro Git 中文版的起步与 Git 基础。
  • GitHub 是托管 Git 仓库并支持协作的平台，可以用来共享公开代码、提交修改和查看项目历史。入门可参考 GitHub Get Started。
  • 数据清单 (manifest) 不替代 Git，它记录某次分析实际使用了哪一批输入文件、它们来自哪里以及版本如何识别。

把这三者配合起来，才能区分一次结果变化究竟来自数据更新、代码修改，还是研究口径调整。相比之下，只保存一个名为 最终版.xlsx 的文件，虽然方便打开，却几乎没有留下这些过程信息。

对初学者而言，暂时不必掌握复杂分支策略。先理解一个最小工作流即可：

  1. 取得仓库：用 git clone 获取已有项目，或在本地项目中初始化 Git。
  2. 查看变化：修改文件后用 git status 和 git diff 看清楚改了什么。
  3. 形成版本：用 git add 选择本次要记录的变化，再用 git commit 写入一个可回溯版本。
  4. 同步远程：需要协作或备份时，再用 git push 把本地提交同步到 GitHub 等远程仓库。

课程环境中终端与 Git 命令的使用也可参见《金融数据分析》的 Python 安装常见问题。

对于 CSMAR 一类受授权限制的数据，版本控制的重点不是把原始数据上传到 Git，而是留下足够的识别信息，例如文件名、来源说明、下载条件和文件指纹，并让处理代码知道应该到授权目录中寻找哪些输入。即使使用 Git LFS，本质上仍然是在分发文件，不能因此绕过数据库的授权限制。

软件环境也有同样的问题。复现并不等于把所有包升级到最新版，更稳妥的做法是先记录并恢复已经验证过的包版本组合，再判断是否需要升级。

2.4.3 从对话建议到 Agent 执行

Agent 的出现让很多数据操作可以交给模型连续执行，但这并没有取消研究者的判断责任。一次典型的 Agent 任务可能包括读取资料、安排步骤、调用代码或命令、观察执行结果，再根据结果调整下一步。它能否读取某个文件、访问某个网站或运行某段程序，取决于具体运行环境和权限，而不是产品名称本身。

因此，评价 Agent 的工作不能只看最后那段任务已完成的总结。更可靠的做法是检查它实际读取了什么、运行了什么、输出了哪些可核对的证据，以及哪些地方仍然需要人工决定。

分析环节 可以委托的工作 学生须判断的内容
问题与资料 整理候选数据需求、查找文档 需求是否对应研究问题，来源是否可靠
获取与读取 编写读取代码、记录参数和来源 授权、样本条件和字段定义
管理与清洗 检查键、转换已确认类型、生成审计 何时允许删除、填补或重新编码
模型与报告 编码、排错、整理输出与文字 识别假设、推断、数量级和结论边界

这里最容易出错的是「任务做完了，但问题没有回答」。例如，我们真正关心的是补贴是否促进了企业研发，却只给 Agent 一句「回归研发对补贴」。它完全可能生成一个能运行的回归程序，并把系数解释得很完整，但这仍然没有解决补贴是否具有因果作用的问题。

所以，交给 Agent 的任务最好同时说明研究目的、允许它执行的操作，以及完成任务时必须提供哪些验收证据。AI 可以高效地整理资料、生成代码和做初步核对，但涉及变量定义、识别假设和文献解释的关键判断，仍需要研究者回到原始资料中核实。

2.5 数据在哪里？

明确了研究问题以后，下一步才是寻找数据。金融数据的来源很多，从学校订阅的商业数据库，到官方统计网站、开源接口和论文复现档案都可能用到。与其一开始就背很多数据库名称，更实用的做法是先理解这些来源各自解决什么问题、有哪些访问限制。

本节沿用《数据分析与经济决策》数据在哪里中的分类和资源表，并结合本课程的金融计量任务补充授权、历史版本和信息口径方面的要求。

2.5.1 金融数据的现实格局

在券商、基金、银行或高校研究中，Wind、Bloomberg、CSMAR 等商业数据库是很常见的数据入口。它们已经替用户完成了大量收集、整理和标准化工作，因此在查找上市公司财务、市场行情、宏观指标和公司治理信息时往往很方便。

但学校能够访问 CSMAR，并不意味着其中所有子库、所有历史区间和全部接口都已经开通。实际能够下载什么，仍然取决于机构订阅范围和具体授权。因此，研究记录里最好写清楚使用的是哪个数据库模块、哪个导出批次和哪些筛选条件，而不是只写一个数据库名称。

对在校学生而言，最省力的起点通常是学校图书馆已经购买的数据库和课程已经分发的数据。本单元的上市公司案例使用 CSMAR，课堂提供的是一个已经按授权导出的特定批次。拿到这些文件以后，仍然要查看字段说明、报表口径和样本期间，因为数据来自 CSMAR 并不能替代变量定义。

账号和密钥属于访问凭证，不应该交给 Agent 代管。Agent 可以在已有授权文件上帮助读取、整理和检查，但访问权限本身应由用户在自己的环境中配置。

如果没有商业数据库，公开机构和开源接口仍然提供了大量可用资料。例如世界银行、FRED、国家统计局等提供官方统计，AKShare、yfinance 等工具则把某些在线数据访问过程封装成 Python 函数。它们非常适合教学，也能支持不少正式研究。

不过，开源、免费、无需注册和允许再分发不是同一回事。开源通常指软件代码的许可，数据本身可能有另外的使用条款；能够免费下载，也不代表可以把原始数据重新公开。因此，使用前仍要看清数据来源和许可范围。

2.5.2 四类数据来源

寻找数据时，可以先把常见入口分成下面四类。这个分类不是质量排名，而是帮助我们判断数据由谁生产、通过什么方式取得，以及正式使用前还需要补哪些核对。

  • 商业数据库：Wind、Bloomberg、CSMAR 等已经替用户完成了大量收集、匹配和整理工作，并提供比较系统的主题划分和字段文档。它们适合快速取得标准化的市场与公司数据，但同名字段仍可能对应不同报表类型、调整方式或历史版本，正式使用前要同时核对定义与授权。
  • 开源 Python 数据接口：AKShare、yfinance 等工具把许多网页访问步骤封装成函数，便于重复调用。需要记住，这些包通常只是访问工具，而不是原始数据生产者；上游网站一旦调整字段、权限或页面结构，接口结果也可能随之改变。因此，除了记录包版本，还应保存实际调用的函数、参数和上游来源。
  • 官方机构及其接口：世界银行、FRED、国家统计局等是宏观与金融研究的重要入口。这类数据通常有较清楚的定义和来源，但仍要阅读元数据，特别是名义值与实际值、季调与未季调值以及历史修订规则。如果研究关心市场参与者当时能够看到的信息，还要进一步处理数据修订问题。
  • 数据平台和学术档案：Kaggle、Harvard Dataverse、ICPSR 以及期刊复现仓库经常同时提供数据、代码和项目说明。它们很适合用来学习变量定义、样本筛选和复现流程，但开放程度并不相同：有的只公开代码，有的公开加工数据，有的原始输入仍来自受限数据库。能够下载，不等于可以任意再发布。

论文复现资料尤其值得利用，因为它把最终结果背后的数据处理过程部分暴露出来。拿到一个复现包以后，不要只打开作者已经整理好的最终分析表；README、变量说明和生成脚本往往更有价值，它们会告诉我们原始数据来自哪里、怎样合并、哪些样本被排除以及变量如何构造。

2.6 从文件与 API 取得可检查的数据

找到合适的数据源以后，真正的获取过程通常只有几种基本形式：读取已经下载到本地的文件，直接读取网络文件，或者通过 API 按参数请求数据。函数很多，但背函数名不是本节的重点。更重要的是形成一套稳定习惯：先确认拿到的是什么，再把数据读进来，看清结构，最后把本次输入保存成可复查的快照。

下面把来源讲义第 9.2–9.4 节合并起来讲。无论使用哪一种工具，都可以沿着这条主线理解。

2.6.1 本地文件：先检查路径、编码和类型

很多金融数据最终都会先以文件形式落到硬盘，例如 CSMAR 批量导出、统计年鉴和论文复现资料。本小节只处理一个问题：怎样把数据提供方交付的文件正确读入分析环境。至于中间数据长期保存为 CSV、Parquet 还是数据库文件，下一讲再从数据契约和复用角度比较。

常见输入包括 CSV、Excel、Stata 的 DTA 和 Parquet。这里没有必要为了形式统一而先把所有原始文件转成同一种格式；更稳妥的做法是保留原始下载文件，按照各自格式核对读取结果，再根据后续任务另存派生数据。

输入 pandas 常见读取入口 第一次读入尤其要检查
CSV read_csv 编码、分隔符、证券代码、缺失标记
Excel read_excel 工作表、表头位置、脚注和合并单元格
Stata read_stata 标签、类别、日期和扩展缺失值转换
Parquet read_parquet 字段结构 (schema)、读取列及当前数据版本

文件能成功读入只是第一步，还要确认关键字段有没有在读取过程中被改变。证券代码就是最典型的例子：000001 的前导零具有标识意义，因此通常应按字符串保存。如果读取器把它自动解释为整数 1，后续确实可能需要补零，但补几位必须依据该数据库的编码规则，不能看到数字标识符就一律调用 zfill(6)。

日期也一样。把字符串转成日期以后，应统计有多少记录转换失败，并追查失败原因，而不是用某个任意日期去填补。完整的离线读取、合并和存储例子见 Notebook 的教学小表，课堂上不需要为了演示这一步实时调用 API。

数据读进来以后，不要马上开始回归。第一次读取可以按下面的顺序做四项检查；每一步解决的问题不同，不能只做到程序不报错就停止。

  1. Step 1: 用 shape 核对行数和列数，先判断文件是否读全。
  2. Step 2: 查看前几行，识别多层表头、单位说明或脚注是否被误当成数据。
  3. Step 3: 检查变量类型与非缺失数量，确认标识变量、日期和数值字段没有在读取时被误解释。
  4. Step 4: 查看必要的描述统计，用数量级和取值范围继续检查单位、异常编码和明显错误。

这四步对应的是从结构到数值含义的逐层核对。处理受限数据时，详细检查可以在授权环境中完成，公开 Notebook 只保留必要的汇总结果。

读取文件时，最常见的问题通常不复杂，但处理方法应当有顺序。课堂上可以把它们分成三类来判断：

  • 路径错误：出现 FileNotFoundError 时，先看当前工作目录，再核对相对路径到底从哪里开始计算。
  • 编码错误：出现中文乱码时，先查看数据提供方对编码的说明，再有依据地尝试 utf-8、gbk 等可能编码。
  • 特殊缺失或占位符：本应为数值的字段中出现 --、N/A 等符号时，先查清它在该数据源中的定义，再决定是否转换为缺失值。

这三类问题看起来都可能表现为读取失败或类型异常，但修复依据不同，因此不应靠反复更换参数碰运气。

读入成功不等于解释正确

不断修改 read_csv() 的参数，直到程序终于不报错，并不能证明数据已经读对。程序能够运行，只说明语法和输入形式被接受；真正要核对的是字段、类型、单位和缺失含义是否与原始说明一致。

2.6.2 在线文件与 API：入口、参数和响应

在线读取时，先要区分浏览器展示页面和程序真正要下载的数据文件。以 GitHub 为例，普通文件页面返回的是用于展示代码的 HTML 页面，Raw 链接返回的才是文件本身。其他网站也有类似情形：一个 URL 在浏览器中能够打开，并不意味着它返回的内容就是我们期待的 CSV、DTA 或 JSON。

因此，比较稳妥的下载流程是先检查 HTTP 状态，再看响应类型和实际内容是否符合预期，确认无误后再保存原始字节，同时记录下载时间和文件校验值。若服务器返回的是登录页、权限提示或错误页面，应把这次请求视为失败，而不是把返回的 HTML 强行交给 pandas 继续解析。访问受限数据时，也不应通过伪装请求头等方式绕过明确的权限控制。

API (Application Programming Interface) 可以理解为数据提供方为程序开放的一套标准入口。沿用来源讲义中的点餐类比，endpoint 相当于点餐入口，parameters 告诉服务器我们要什么，认证信息说明是否有访问权限，response 则是服务器返回的数据。

这个类比有助于理解调用过程，但还要记住：API 只是访问方式，不等于数据天然免费、实时或完整。有的接口需要认证，有的限制调用频率，有的单次只返回固定数量的记录，还可能需要分页。真正使用时，应以官方文档说明为准。

  1. Step 1: 根据官方文档明确端点或函数、参数、频率、单位与权限。
  2. Step 2: 先请求很小的时间范围，核对字段、数量和日期。
  3. Step 3: 按文档处理分页、超时和访问频率限制，记录失败批次，不把失败当零条数据。
  4. Step 4: 保存输入快照、请求参数、版本和下载日期，后续分析读取该快照。

如果接口需要 API key，应把密钥配置在用户自己的环境变量或受保护配置中，不要写进提示词、Notebook 输出或 Git 仓库。这样既避免泄露，也便于在不同机器上使用同一份代码。

还要把持续更新数据和课堂复现分析分开。持续更新任务可以定期调用接口并生成新的输入快照；课堂或论文复现则更适合读取一份已经检查过的固定快照。否则，同一段代码在不同日期运行得到不同输入，很难判断结果变化究竟来自模型还是数据更新。

2.6.3 AKShare：以历史行情理解参数

AKShare 是一个很适合用来理解 API 参数的例子。它把若干金融数据访问过程封装成 Python 函数，用户不需要自己拼接复杂的网络请求。以股票接口官方文档中的历史行情函数 stock_zh_a_hist 为例，symbol 决定证券，period 决定频率，start_date 与 end_date 决定时间范围，adjust 则涉及价格调整方式。

这些参数看起来只是函数选项，其实都对应研究口径。尤其要区分今天能查到的股票名单和过去某一天实际存在的可投资集合。如果用当前股票列表回溯历史，已经退市的证券可能从一开始就被排除，形成明显的事后选择。

参数或选择 读者必须说明
股票与日期范围 选择是否依赖事后表现；边界是否包含所需支持期
日、周、月频率 使用交易频率还是财务报告频率
不复权、前复权、后复权 价格调整依据与研究用途
成交量、金额、涨跌幅 原始单位以及百分数与小数的区别

复权参数尤其容易被当成一个应该选哪个的技术问题。其实，它对应的是我们希望价格序列表达什么。考虑一个最简单的现金分红例子：某股票前一日价格为 10 元，除息后价格降到 9 元，同时每股支付 1 元现金。忽略税费，如果把现金分红计入投资者回报，则回报为 (9+1)/10-1=0；如果只看价格变化，则会得到 −10%。

这个例子说明，除权除息会造成机械的价格跳变，因此研究收益时必须明确是否以及怎样处理公司行为。但它并不意味着某一种前复权或后复权价格在所有任务中都天然正确，最终仍要回到变量定义和研究用途。

前复权和后复权本质上选择了不同的价格标度。具体调整因子如何计算、现金分红怎样处理、历史序列会不会随着后来公司行为而重新调整，都应查看接口或数据源说明。尤其不能把后复权价格直接理解为当时市场上能够成交的真实价格，也不能因为保存了一份复权历史序列，就认为前视偏误已经自动消失。

来源讲义中的实时接口代码仍可作为学生课后查询的入口；本书课堂演示则使用冻结的数据快照，以保证同一节课中的输入一致。本轮没有重新测试所有实时端点，因此不把接口当前可用性写成已验证事实。

2.6.4 写给 Agent 的获取任务

如果把数据获取交给 Agent，提示词最好不要只写「帮我下载股票数据」。一个可执行的获取任务，至少要告诉它研究对象和期间，要求它先核对官方文档，并规定怎样证明下载结果是完整而且可追溯的。研究范围仍由研究者决定，例如股票池不能由 Agent 根据事后表现自行挑选。

下面给出一个可以直接改写的模板。重点不在措辞本身，而在于把来源、参数、权限、失败记录和验收证据都写进任务。

权限、分页和可能的修订规则，供我核对。
只在指定项目目录工作；不读取账号或密钥；不覆盖已有快照。
先用短期间检查字段和日期；不得把请求失败记为零观测。

这里把获取成功定义得比较严格，是因为一张能够画出来的走势图并不能证明输入已经可靠。至少要确认文件确实保存下来，字段含义和请求参数有记录，失败批次没有被悄悄忽略。只有这些信息齐备，下一章讨论怎样管理、聚合和连接多张表时才有可靠起点。

2.7 本地运行与学习安排

学生可以先在线阅读，再 clone FinEco 仓库，在自己的工作副本运行 Notebook。首次获取可使用下列命令；已有副本不要重复 clone 到同名目录。

git clone https://github.com/lianxhcn/FinEco.git
cd FinEco

按课程环境说明选择正确的 Python 内核，依赖清单见本单元依赖。Notebook 的第 00 节给出数据根目录与运行说明。代码和文档随仓库提供，CSMAR 原始文件由教师按授权渠道另行分发，clone 不会下载受限数据库。

也可以下载已保存输出的 Notebook 源文件，但运行仍依赖仓库中的工具脚本和授权输入，因此建议保留完整仓库结构。

课堂上不需要把本讲所有工具逐一讲完。更适合重点讲清楚的是分析流程、数据来源的基本地图，以及一次数据获取怎样做最初检查。具体工具表可以留给学生课后查阅。

自学时，可以先写一页自己的数据需求说明。至少写清楚：

  • 研究对象是谁；
  • 时间范围是什么；
  • 一行数据希望代表什么；
  • 需要哪些关键字段；
  • 这些字段在什么时候能够获得；
  • 准备从哪里取得，是否存在授权限制。

写完这张数据需求单以后，再进入数据管理，会更容易理解为什么后面要反复强调粒度、主键和版本。
