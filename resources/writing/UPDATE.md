# 增加 S04 与修改规则

## 1. 两类更新

原书观察更新，修改 sources 中对应卡片；项目采用方式变化，修改 GUIDE。二者可以同时发生，但不能把新书所有习惯直接追加为项目规则。

## 2. 增加 S04

1. **Step 1**：记录书名、版本、可访问来源、实际读过的章节与页码。原书观察与编辑建议分开。
2. **Step 2**：在 sources 中创建 `S04-具体短名.md`，按 SOURCE-TEMPLATE 记录。无来源或无页码时写未核对，不补造证据。
3. **Step 3**：与 GUIDE 对照：哪些只是新增依据，哪些补充适用场景，哪些与已有要求冲突，哪些确需新规则。
4. **Step 4**：在规则修改任务中提交具体改法和影响章节。已有用户指令足以授权的修改直接完成；只是候选且改变已确认结构或结论时先保留候选，不能自行全书替换。
5. **Step 5**：更新 GUIDE、RULE-MAP、README、CHANGELOG 和相应示范/验收项。使用稳定文件名与项目 Git 保存历史。
6. **Step 6**：在一处代表性段落或样章试用，核对收益与代价。按实际任务继续推进，不为新增来源自动触发全书重写。

## 3. 用户直接修改规则

用户可以说：

> 把主案例连续性规则改成：每章允许两个主案例，但同一推理段落不切换。请修改现行指南、示范和验收项，列出受影响章节；先不要修改已确认正文。

Codex 应查找对应规则，更新原条目，明确条件，不在文件末尾再追加一条相反规则。术语修正同样追踪正文、公式、图形和代码中的对应位置。

## 4. 影响范围与已确认内容

| 变化 | 默认处理 |
|---|---|
| 来源卡片增加证据，项目规则没变 | 不改正文 |
| 语言和解释要求变更 | 后续新写使用；已有内容按用户指定范围修订 |
| 数学、识别、单位等准确性问题 | 立即记录具体影响，准备必要修复；不掩盖已确认文本中的技术问题 |
| 案例、章节顺序或核心结论变更 | 提供差异与影响清单，按用户授权范围执行 |

已确认章节注明确认时规则版本，并记录新规则待复核项，不能无声覆盖。

## 5. 版本与读取

初始 0.1.0 为试用基线。结构或原则变化可递增次版本，文字澄清可递增补丁版本；经样章校准后再标为正式。版本号用于追踪，不表示自动获得作者确认。

新任务实际读取最新索引和指南；正在运行的任务收到更新后显式重读。入口 AGENTS 改变后启动新任务并完成读取检查。

## 6. 何时制作 Skill

在同一项目持续写书，用短 AGENTS 入口与项目规则即可。将流程复用于多个教材、讲义或由他人安装时，才考虑 Skill。

Skill 封装“读取项目指南 → 设计 → 写作 → 验收 → 更新”的通用工作流。项目 GUIDE、样章和规则历史仍在项目中，Skill 不维护第二套副本，也不把原书 PDF 打进安装包。当前包没有创建或安装 Skill。
